# HFFN GPU runtime on NVIDIA (CUDA): isolated FFN inference

The isolated Hidden-FFN (HFFN) forward on CUDA: one sparse feed-forward block `y = W_down gelu(W_up x + b_up) + b_down`
with a fixed support, stored and executed by hidden neuron. This leaf is the FFN counterpart of
[`llm/inference`](../../llm/inference/README.md); both run the same kernels, which live at the shared level
[`gpu/nvidia/common/kernels`](../../common/kernels/README.md).

Results: [RESULTS.md](RESULTS.md).

## Scope

| | |
|---|---|
| Degree of optimisation | **a port, not a tuned kernel set.** The kernels, their work distribution and their selection thresholds are those first measured on the Apple M1 GPU; the down width bound (4096) was swept on a T4 at `d_ff` 3072 and 4096. No kernel or threshold was tuned for CUDA. |
| Hardware | An NVIDIA GPU with CUDA 12, one device (`cuda:0`), PyTorch's default stream; kernels compiled at run time by NVRTC through CuPy. Measured on one Tesla T4 only. |
| Models | An isolated FFN given by its compact arrays; `d_model` a multiple of 16, indices 16-bit (`d_model`, `d_ff` below 32 768). Embedded test layers: `homog_256_1024`, `homog_512_2048` (homogeneous supports) and `irreg_512_2048` (irregular support, exact offsets), about 10 % density, regenerated by the deterministic generator of `common/ffn`. Timed cells: the `512_2048` FFN at densities 5 to 100 % and the `256_1024` and `1024_4096` FFNs at d10. |
| Results | [RESULTS.md](RESULTS.md). |

## What it computes

Hidden neuron `r` owns its active incoming connections, its bias and its active outgoing connections. The kernels read the
compact arrays (values, indices, offsets) on the device and never build a dense `W_up` or `W_down`. `x`, `z`, `h`, `y` and
the work buffers are dense, shared by the layers and reused. One call processes the whole block of `N` tokens. The result
equals the sparse FFN up to float32 reduction order.

Kernels, selected by `N` (`up_mode` and `down_mode` of `hffn_cuda/runtime.py`; every pair can be forced for the checks):

- up: `coop` for `N` <= 4, `lane` for 4 < `N` < 64, `tile` for `N` >= 64;
- down: `coop` for `N` <= 4; `blocked` for `N` >= 64 when `d_ff` <= 4096 or `N` <= 128; `tiled` otherwise.

The GPU keeps its own dispatch and reduction policies; the CPU grouping is not transposed.

## Contents

```
hffn_ffn_cuda/        the leaf entry: cuda_layer(layer) turns a test layer into the HFFNLayer the runtime consumes
checks/parity.py      per layer and N: repeatability, distance to float64, the nine forced kernel pairs and the policy
check.sh              layer fingerprints, then checks.parity; writes runs/check_<UTC>/ (check.log, manifest.json, EXIT)
launch.sh             check.sh with a log that opens with the GPU, the versions and the source hashes
bench/                a timing script of the leaf (arms dense, dense_copy, hffn, hffn_copy in ABBA blocks) with its launcher
tools/provenance.py   tree digest and per-file hashes of the shared kernels, the shared test layers and this leaf
requirements.txt      torch, cupy-cuda12x, numpy
```

The entry puts the shared `hffn_cuda` and `hffn_ffn_layers` on `sys.path`, each found as the first ancestor folder that
holds it: use and copy the `runtime/` tree.

## Run

Needs a CUDA machine and the environment of `requirements.txt`; nothing is read from assets.

```bash
./check.sh                         # the check, about half a minute on a T4
./launch.sh                        # the same, with a log opened by the GPU and the source hashes
python -B tools/provenance.py      # tree digest and number of files
python -B -m checks.parity         # the parity alone
```

`check.sh` ends with `check: PASSED` or `check: FAILED`. For each test layer and each `N` in 1, 2, 4, 5, 7, 8, 32, 63, 64,
96, 128, 129, 256, 512, with the runtime policy and with each of the nine forced (up, down) pairs: two consecutive calls
give the same bits, and `max|y - y_float64| <= 2e-5` against the float64 oracle of the same fixed-support FFN. The distance
of the dense float32 control and the bit identity of the four sequential pairs are printed without a threshold.

`bench/vm_run.sh smoke|run` is the timing script's launcher; a timing run needs a protocol of its own and is not part of the
check. The published figures were produced by another bench that is not distributed (see `RESULTS.md`).

## Known limits

- **Without a GPU nothing runs:** the leaf cannot be verified on a machine without CUDA.
- **A port:** the dense control is PyTorch eager (separate GELU, per-call allocations), and at small `N` both arms are
  host-bound, so a ratio partly measures launch count and dispatch. It is not a claim of being faster than dense.
- **One Tesla T4** on a shared cloud VM; `delta` is reported, not applied. Compare within one execution only, never with
  M1 or x86 figures.
- **Boundary of the format:** at high density the HFFN arm is slower than dense (RESULTS.md).
- Several optimisation proposals estimated above 2 % are not done; they are limits of this version.
